# ADR-0005: Outbox パターンによるイベント発行保証

## ステータス

承認済み

## コンテキスト

マイクロサービスアーキテクチャにおいて、DB へのデータ書き込みと Kafka へのイベント発行を原子的に行う必要がある。DB コミットは成功したがイベント発行が失敗した場合、データの不整合が発生する。逆にイベントを先に発行して DB コミットが失敗した場合、誤ったイベントが伝搬される。

## 決定

**Outbox パターン** を採用する。イベントを直接 Kafka に発行するのではなく、DB トランザクション内で `outbox_events` テーブルにイベントレコードを書き込み、`OutboxPublisher`（BackgroundService）が定期的にポーリングして Kafka に発行する。

## 理由

### 検討した代替案

| 代替案 | メリット | デメリット |
|-------|---------|----------|
| **Outbox パターン + ポーリング（採用）** | DB トランザクションとイベント発行の原子性保証、実装がシンプル | ポーリングによるレイテンシ、DB 負荷 |
| **CDC（Change Data Capture / Debezium）** | リアルタイムなイベント配信、DB ポーリング不要 | インフラ複雑性（Debezium + Kafka Connect の運用）、学習コスト |
| **Dual Write（DB + Kafka 同時書き込み）** | 実装がシンプル | 原子性の保証不可、データ不整合リスク |
| **Event Sourcing** | イベントが正（Single Source of Truth） | 実装複雑性が非常に高い、CRUD ベース設計との不整合 |

### 選択理由

1. **原子性の保証**: Outbox テーブルへの書き込みは DB トランザクション内で行われるため、データ書き込みとイベント記録の原子性が保証される
2. **実装のシンプルさ**: EF Core の `SaveChangesAsync` + `outbox_events` テーブルで実装可能
3. **冪等性**: `AggregateId` をキーにイベントの重複排除が可能
4. **CDC への移行パス**: 将来的にピーク TPS が 1,000 を超過した場合、CDC（Debezium）への移行が可能（中長期 TODO として記録）

## 結果

### ポジティブ

- DB トランザクションとイベント発行の原子性が保証され、データ不整合を防止
- 動的ポーリング間隔（100ms〜5s 指数バックオフ）により、低レイテンシと低 DB 負荷を両立
- `outbox_events` テーブルの部分インデックスにより、未発行イベントの高速取得が可能

### ネガティブ

- ポーリングによる若干のレイテンシ（100ms〜5s）が発生
- `outbox_events` テーブルの肥大化対策（処理済みイベントのアーカイブ/削除）が必要
- 高 TPS 時に DB ロック競合・WAL 肥大化のリスクがあり、CDC への移行検討が必要（中長期 TODO）
