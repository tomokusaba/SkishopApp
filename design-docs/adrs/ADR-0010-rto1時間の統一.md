# ADR-0010: RTO 1 時間の統一

## ステータス

承認済み

## コンテキスト

SkiShop プラットフォームは 11 のマイクロサービスで構成されており、各サービスの障害がビジネスに与える影響度が異なる。しかし、サービスごとに異なる RTO（Recovery Time Objective: 復旧目標時間）を設定すると、運用の複雑性が増大し、SRE チームの対応手順が煩雑になる。

EC サイトという特性上、ダウンタイムは直接的な売上損失に直結するため、迅速な復旧が求められる。一方で、過度に短い RTO はインフラコストと運用負荷を増大させる。

## 決定

全マイクロサービスに **RTO 1 時間** を統一的に適用する。このために以下の技術的施策を実施する。

### 復旧戦略

| 施策 | 実装方法 | 目的 |
|------|---------|------|
| データベースバックアップ | PostgreSQL WAL アーカイブ + 日次フルバックアップ（Azure Blob Storage） | RPO 5 分以内のデータ復旧 |
| サービス冗長化 | Kubernetes `minReplicas: 2`、ヘルスチェック `/health`・`/health/ready` | ゼロダウンタイムデプロイ |
| DB フェイルオーバー | PostgreSQL ストリーミングレプリケーション + 自動フェイルオーバー | DB 障害時 5 分以内の自動切替 |
| メッセージング | Kafka `replication.factor=3`、`min.insync.replicas=2` | メッセージの永続性保証 |
| キャッシュ復旧 | Redis Sentinel によるフェイルオーバー + Cache-Aside パターン | キャッシュ障害時の自動 DB フォールバック |
| 障害検知 | OpenTelemetry + Prometheus Alert（5 分以内検知） | 人的介入開始までの時間短縮 |

### 障害レベル別の対応フロー

| レベル | 影響範囲 | 復旧手順 | 目標時間 |
|-------|---------|---------|---------|
| L1（Pod 障害） | 単一 Pod | Kubernetes 自動再起動 | 1〜3 分 |
| L2（サービス障害） | 単一サービス | ロールバックデプロイ + DB リカバリ | 15〜30 分 |
| L3（インフラ障害） | 複数サービス | フェイルオーバー + 手動介入 | 30〜60 分 |
| L4（全面停止） | 全サービス | DR サイトへの切替（将来対応） | 1 時間 |

## 理由

### 検討した代替案

| 代替案 | メリット | デメリット |
|-------|---------|----------|
| **RTO 1 時間統一（採用）** | 運用手順がシンプル、SLO の管理が容易、コストと復旧速度のバランスが良い | 重要度の低いサービスに過剰投資の可能性 |
| **RTO 30 分統一** | より迅速な復旧、ユーザー影響の最小化 | Active-Active 構成が必須となりコストが 2〜3 倍、運用複雑性が高い |
| **RTO 4 時間統一** | インフラコスト削減、運用負荷低減 | EC サイトとして売上損失が大きい（ピーク時に 4 時間停止は許容不可） |
| **サービス別 RTO** | 各サービスの重要度に応じた最適化 | 運用複雑性の増大、SRE チームの負荷増加、障害時の判断遅延 |

### 選択理由

1. **運用のシンプルさ**: SRE チームが 1 つの RTO 基準で全サービスの復旧を判断。障害時の意思決定が迅速になる
2. **コスト対効果**: Active-Passive 構成 + 自動フェイルオーバーで 1 時間 RTO を達成可能であり、Active-Active のコストを回避
3. **EC サイトのビジネス要件**: 1 時間を超えるダウンタイムは顧客離脱率が急上昇する（業界ベンチマーク）ため、4 時間は不適切
4. **段階的改善の余地**: 将来トラフィック増加時に、認証・決済などクリティカルサービスのみ RTO を短縮する段階的な対応が可能

## 結果

### ポジティブ

- 全サービスの SLO が統一され、監視アラートの閾値設定が一本化される
- 障害対応ランブックが 1 セットで済み、SRE チームのオンコール負荷が軽減される
- RPO 5 分 + RTO 1 時間の組み合わせにより、データ損失リスクとダウンタイムの両方を許容範囲内に抑制

### ネガティブ

- MailSendService や AiSupportService など重要度の低いサービスにも同等のインフラ投資が必要
- DR サイト（L4 対応）は Phase 2 以降の対応となり、初期リリースでは全面停止時に 1 時間を超える可能性がある
- PostgreSQL の WAL アーカイブとフルバックアップのストレージコストが発生する
