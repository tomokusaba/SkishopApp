# ADR-0001: マイクロサービスアーキテクチャの採用

## ステータス

承認済み

## コンテキスト

SkiShop EC プラットフォームは、商品カタログ、在庫管理、注文処理、決済、ユーザー管理、ポイント、クーポン、AI サポート、メール送信など多岐にわたるドメインを持つ。将来的にはトラフィック増加、機能追加、チーム拡大が見込まれており、アーキテクチャの選択がプロジェクト全体の開発速度・運用性・スケーラビリティに直結する。

## 決定

モノリシックアーキテクチャではなく、**マイクロサービスアーキテクチャ** を採用する。各ビジネスドメイン（認証、ユーザー管理、在庫管理、販売管理、決済・カート、クーポン、ポイント、メール送信、AI サポート）を独立したサービスとして実装し、API Gateway（YARP）を経由して統合する。オーケストレーションには .NET Aspire 13.1 を使用する。

## 理由

### 検討した代替案

| 代替案 | メリット | デメリット |
|-------|---------|----------|
| **モノリシックアーキテクチャ** | 開発初期のシンプルさ、デプロイの容易さ、トランザクション管理の単純さ | スケーリングの柔軟性不足、チーム並行開発の困難さ、障害の影響範囲が全体に波及 |
| **モジュラーモノリス** | モノリスの単純さを維持しつつドメイン分割が可能 | 将来のサービス分離が容易ではない、独立デプロイ不可、DB 共有による結合度の高さ |
| **マイクロサービス（採用）** | 独立デプロイ・スケーリング・障害分離、技術スタックの柔軟性、チーム自律性 | 分散システムの複雑性、運用コスト増、サービス間通信のオーバーヘッド |

### 選択理由

1. **独立デプロイ**: 各サービスを独立してデプロイでき、リリース頻度を高められる
2. **独立スケーリング**: 高負荷サービス（API Gateway、在庫管理、決済）を個別にスケーリング可能
3. **障害分離**: 1 つのサービスの障害が他サービスに波及しない設計が可能
4. **チーム並行開発**: 複数チームがサービスごとに並行して開発できる
5. **.NET Aspire 13.1**: .NET エコシステム内でマイクロサービスの開発・運用を効率化するオーケストレーション基盤が成熟

## 結果

### ポジティブ

- 各サービスが独立してデプロイ・スケーリングでき、ビジネス要件の変化に迅速に対応可能
- 障害のブラスト半径が限定され、サービスレベル目標（SLO 99.95%）の達成に寄与
- .NET Aspire によるローカル開発・テスト環境の構築が容易

### ネガティブ

- 分散トランザクション管理に Saga パターン（ADR-0009 参照）が必要
- サービス間通信のレイテンシと信頼性の管理が必要（Polly によるリトライ・サーキットブレーカー）
- 運用・監視の複雑性が増す（OpenTelemetry + Serilog + Aspire Dashboard で緩和）
- Outbox パターン（ADR-0005 参照）によるイベント発行の原子性保証が必要
