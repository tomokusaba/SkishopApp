# ADR-0003: PostgreSQL の全サービス統一採用

## ステータス

承認済み

## コンテキスト

マイクロサービスアーキテクチャでは各サービスが最適なデータストアを選択する「Polyglot Persistence」が一般的だが、SkiShop プロジェクトでは運用の統一性、チームのスキルセット、学習コストを考慮してデータストアの選定を行う必要がある。

## 決定

全マイクロサービスの RDBMS として **PostgreSQL** を統一採用する。EF Core 10 + Npgsql プロバイダーでアクセスする。各サービスは論理的に独立した DB を持つ（ADR-0006 参照）。

## 理由

### 検討した代替案

| 代替案 | メリット | デメリット |
|-------|---------|----------|
| **PostgreSQL（採用）** | JSONB、全文検索、パーティショニング、豊富な拡張機能、OSS、Azure Flexible Server 対応 | NoSQL に比べた水平スケーリングの制約 |
| **SQL Server** | .NET エコシステムとの深い統合、Azure SQL の成熟度 | ライセンスコスト、OSS コミュニティの規模 |
| **Polyglot（PostgreSQL + MongoDB + Redis）** | 各サービスに最適なデータストア選択 | 運用複雑性の大幅増加、チームスキルの分散 |

### 選択理由

1. **機能の豊富さ**: JSONB（半構造化データ）、GIN インデックス（全文検索）、pg_trgm（あいまい検索）が EC サイトの要件を満たす
2. **コスト**: OSS でありライセンスコスト不要。Azure Database for PostgreSQL Flexible Server でマネージド運用可能
3. **EF Core 10 との互換性**: Npgsql プロバイダーが成熟しており、EF Core の全機能を活用可能
4. **運用の統一**: 全サービスで同一の RDBMS を使用することで、バックアップ・監視・マイグレーションの運用手順を統一

## 結果

### ポジティブ

- 運用チームが単一の RDBMS スキルセットで全サービスを管理可能
- Azure Database for PostgreSQL Flexible Server によるゾーン冗長高可用性でSLO 99.95% を支援
- JSONB カラムにより、一部の半構造化データ（AuditLog の `oldValue`/`newValue` 等）を柔軟に格納可能

### ネガティブ

- AI サポートサービスのベクトル検索など、将来的に専用データストア（pgvector 拡張で対応可能）が必要になる可能性
- 水平スケーリングが必要な規模になった場合、Citus 拡張やシャーディング戦略の検討が必要
