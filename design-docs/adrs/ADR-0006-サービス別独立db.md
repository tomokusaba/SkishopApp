# ADR-0006: サービス別独立 DB（Database per Service）

## ステータス

承認済み

## コンテキスト

マイクロサービスアーキテクチャにおいてデータストアの共有方式を決定する必要がある。複数サービスが単一の DB を共有すると、スキーマ変更の影響範囲が広がり、独立デプロイが困難になる。一方、完全なDB 分離はサービス間のデータ参照に制約を課す。

## 決定

**Database per Service** パターンを採用し、各マイクロサービスが専用の論理 DB を持つ。サービス間の DB 直接参照（JOIN、FK 制約）は禁止する。サービス間のデータ参照は API 呼び出しまたは Kafka イベントによる結果整合性で実現する。

## 理由

### 検討した代替案

| 代替案 | メリット | デメリット |
|-------|---------|----------|
| **Database per Service（採用）** | 完全な独立性、独立スキーマ進化、障害分離 | サービス間 JOIN 不可、結果整合性の管理が必要 |
| **共有 DB（単一 skishopdb）** | サービス間 JOIN が容易、トランザクション管理がシンプル | サービス間の密結合、スキーマ変更の影響範囲拡大、独立デプロイ困難 |
| **Schema per Service（同一 DB 内でスキーマ分離）** | ある程度の分離と運用の容易さのバランス | 物理的に同一 DB のため障害が全サービスに波及、スケーリングの制約 |

### 選択理由

1. **独立デプロイ**: 各サービスが独自のスキーマを管理し、他サービスへの影響なく DB マイグレーションを適用可能
2. **障害分離**: 1 つの DB の障害が他サービスに波及しない
3. **スケーリング**: サービスごとに DB のスケーリング（接続プール、レプリカ数）を最適化可能
4. **DDD 原則との整合**: Aggregate Root 単位の Repository パターンと合致

## 結果

### ポジティブ

- 各サービスが独立して DB マイグレーションを実行でき、Expand-Contract パターンでゼロダウンタイムマイグレーションが可能
- .NET Aspire の `AddDatabase` で論理 DB をサービスごとに分離（authdb, userdb, inventorydb, salesdb, paymentdb, coupondb, pointdb, aidb）

### ネガティブ

- サービス間のデータ参照に API 呼び出しが必要（レイテンシ増加）
- 分散トランザクションが不可のため、Saga パターン（ADR-0009）が必要
- マイクロサービス間参照（例: `orders.userId` → ユーザー管理: User）は FK 制約なし、結果整合性で担保
